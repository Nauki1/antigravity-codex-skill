# codex-loop 测试规划与开发规则

本轮目标是建立**可离线执行、能够阻止错误放行、具备验收证据的自动化测试体系**。优先验证审查判定、CLI 调用和会话归档，再补充跨平台兼容性。

## 1. 项目现状与风险

当前可执行源码位于 `scripts/`，主要包含：

| 被测模块 | 职责 | 优先验证内容 |
|---|---|---|
| `codex_loop.py` | 环境探测、规划调用、代码审查 | 参数构造、结果判定、失败传播 |
| `sync_session.py` | 会话发现、内容清洗、Markdown 导出 | 会话选择、内容保真、文件边界 |

仓库尚未建立自动化测试套件和 CI 流程。已完成的基础检查及发现如下：

- 两个脚本的 Python 语法检查、`--help` 命令检查通过。
- 隔离模拟确认：审查输出为 `NOT APPROVED` 时，会被误判为通过。
- 隔离模拟确认：拒绝说明中出现 `lgtm` 时，也会被误判为通过。
- `scripts/codex_loop.py` 存在未提交修改，后续实施必须保留该变更。

**上述审查误判属于 P0 缺陷；基础检查通过不代表业务验收通过。**

## 2. 技术设计

### 2.1 测试分层

采用 Python 标准库 `unittest` 与 `unittest.mock`，降低初期依赖和维护成本。

| 层级 | 实现方式 | 验证目标 |
|---|---|---|
| 单元测试 | 模拟配置、目录、时钟及子进程返回值 | 边界条件、判定规则、参数构造 |
| 集成测试 | 临时目录、合成 JSONL、本地假 CLI | 文件读写、输出通道、退出码传播 |
| CLI 测试 | 启动脚本并捕获输出 | 参数校验、命令分发、错误提示 |
| 真实环境冒烟 | 指定 CLI 版本及测试仓库 | 外部 CLI 兼容性和实际调用链 |

默认测试套件应能离线运行。真实模型调用单独执行、单独记录，不作为普通测试的隐式依赖。

### 2.2 测试目录

建议新增以下结构：

```text
tests/
├── test_environment.py
├── test_plan.py
├── test_review.py
├── test_session_discovery.py
├── test_content_cleaning.py
├── test_session_export.py
├── test_cli.py
└── fixtures/
    ├── transcripts/
    └── review_outputs/
```

测试说明建议维护于 `docs/test-plan.md`。

**目录规则前置事项：**`AGENTS.md` 约定核心代码位于 `src/`，但现有实现位于 `scripts/`。实施前应明确现有工具脚本与测试目录的适用规则；测试建设不附带源码迁移或目录重构。

### 2.3 隔离与数据规范

- 使用 `TemporaryDirectory` 保存测试配置、会话和导出文件。
- 导入被测模块前模拟用户目录，避免导入阶段读取真实配置。
- 配置、鉴权及会话样本均使用合成数据，不读取真实凭证。
- 时间、目录修改时间和子进程响应均可控制，避免依赖机器状态。
- 断言可观察结果：返回值、退出码、文件内容、命令参数和错误信息。

## 3. 测试场景与优先级

### P0：阻止错误放行与归档破坏

| 编号 | 场景 | 预期行为 |
|---|---|---|
| R01 | 输出包含 `NOT APPROVED`、引用的 `lgtm` 或矛盾结论 | 不通过审查 |
| R02 | CLI 非零退出，但输出包含批准文字 | 判为执行失败 |
| R03 | 输出为空、格式未知或缺少明确结论 | 不通过审查 |
| C01 | 审查指定 `--base`，或同时传入自定义说明 | 参数组合符合对应 CLI 版本约束 |
| C02 | 可执行文件缺失、权限不足或调用超时 | 可识别地失败，无无限等待 |
| S01 | “最近会话”中目录时间与 transcript 时间不一致 | 列表与默认选择采用相同排序依据 |
| S02 | JSONL 损坏、记录类型异常或全部无效 | 明确报告异常；不得静默生成成功的空归档 |
| S03 | 正文含嵌套标签、代码块、附件与技能引用 | 保留有效原文，仅清理确定的平台包装 |
| S04 | 标题或会话 ID 含路径穿越内容 | 拒绝隐式越界；显式 `--out` 按指定目标处理 |
| S05 | 写入失败或目标文件已存在 | 错误可见，不损坏已有文件；覆盖策略明确 |

### P1：配置与日常行为

- 二进制探测覆盖各优先级、无候选及多候选情况。
- 模型参数覆盖显式覆盖、默认配置和配置缺失情况。
- 核对文档与实现的差异：文档描述默认继承 CLI 配置，当前代码会显式传入解析得到的模型。
- `plan` 成功输出、失败输出及文件写入行为正确。
- 会话列表限制、中文、空白行、长文本和 Markdown 输出正确。
- 无效命令及缺失参数返回非零退出码。

### P2：兼容性

- Windows 与 Linux 文件路径。
- 含空格及中文的路径。
- 不同工作目录启动。
- UTF-8、CRLF 与 LF。
- 大型会话文件的处理耗时与内存表现。

## 4. 审查与错误处理契约

审查判定应从宽松关键词匹配改为**明确协议校验**：

1. 批准标记必须处于约定的独立结论位置。
2. 否定、引用、代码示例或正文中的批准词不构成通过。
3. 输出存在矛盾、解析失败或执行失败时，不予放行。
4. 协议是本项目包装层的约定，不能假设原生 CLI 必然返回固定格式；需用真实输出样本验证适配。

建议统一包装层退出码：

| 结果 | 退出码 |
|---|---:|
| 规划成功、审查明确通过、归档成功 | `0` |
| 执行失败、文件错误、超时、结果无法解析 | `1` |
| 审查要求修改 | `2` |

参数错误可沿用 `argparse` 的退出码 `2`，通过错误信息区分。该契约属于待实施目标，需同步更新代码、测试及使用说明。

## 6. 质量约束与验收门槛

- **证据门槛：**实际测试命令退出码必须为 `0`，且发现的测试数量大于零。
- **场景门槛：**P0 场景全部通过，无跳过项；P1 未完成项必须明确列出。
- **缺陷门槛：**审查误放行、归档越界和内容丢失等 P0 缺陷清零。
- **真实性门槛：**不得用吞异常、放宽断言或删除失败用例制造通过结果。
- **隔离门槛：**默认套件不访问真实账号、个人会话或真实模型服务。
- **审查门槛：**关键变更通过异构审查；审查不能替代自动化测试。
- **追溯门槛：**保存提交标识、运行环境、执行命令、测试数量、失败与跳过数量及退出码。

测试套件建立后的标准执行命令：

```powershell
python -B -m unittest discover -s tests -p "test_*.py" -v
```
