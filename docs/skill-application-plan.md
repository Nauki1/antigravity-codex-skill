# codex-loop 全局 Skill 技术设计与实施计划

**建议采用“全局安装工具、目标工程保存上下文、双 Agent 串行协作”的架构。** `D:\codex-loop` 负责开发与发布 Skill；Antigravity 和 Codex 在用户指定的 Target Project 中完成业务工作。

本方案基于现有脚本、架构文档和最新 session 制定。本次交付为设计与计划，尚未实施代码变更或验证完整双向调用链。

## 1. 定位与边界

### 1.1 区分三个目录

| 概念 | 职责 | 存放内容 |
|---|---|---|
| **Skill 开发仓库**：`D:\codex-loop` | 开发、测试、发布协同工具 | 源码、Skill 定义、模板、工具测试、开发文档 |
| **Skill 全局安装目录** | 为各宿主提供可调用能力 | 发布后的 `SKILL.md`、脚本、必要参考和模板 |
| **Target Project**：如 `D:\projects\web-app` | 承载业务开发与协作结果 | 原有业务代码、项目规则、任务计划、测试证据、审查记录 |

必须落实以下边界：

- 执行业务任务时，两端共同操作 **Target Project 的同一份文件**。
- Skill 安装目录提供工具，不保存目标工程的代码、任务或会话。
- Skill 开发仓库的 `AGENTS.md`、`.codex/config.toml` 和历史 session 不随发布包注入目标工程。
- Target Project 保持原有目录结构；不能要求所有项目都采用 `src/`、`tests/`。
- 开发仓库可以接入自己的 Skill，但这是一次明确的目标绑定，不能成为其他任务的默认目录。

### 1.2 V1 的范围

V1 支持任意技术栈的本地目标工程，默认使用 Git 完成变更审查与追溯。非 Git 工程可先提供规划能力；是否支持完整自动开发闭环，需要单独确定审查基线。

## 2. 当前实现需要补齐的内容

## 3. 技术设计

### 3.1 全局发布与宿主适配

一个维护来源，生成相同版本的发布包，分别安装到宿主支持的位置：

| 宿主 | 当前官方全局 Skill 目录 |
|---|---|
| Codex | `~/.agents/skills/codex-loop/` |
| Antigravity IDE | `~/.gemini/config/skills/codex-loop/` |
| Antigravity CLI | `~/.gemini/antigravity-cli/skills/codex-loop/` |

Codex 与 Antigravity 都支持项目级 `.agents/skills/`。因此，整个 `.agents/` 不能定义为 Antigravity 独占目录。上述路径应由安装适配器按宿主版本验证；本机已有 `.codex/skills` 属于需要检查的兼容场景。[Codex Skill 文档](https://learn.chatgpt.com/docs/build-skills)、[Antigravity Skill 文档](https://www.antigravity.google/docs/skills?tab=ide)

发布包建议包含：

```text
codex-loop/
├── SKILL.md                 # 触发条件、工作流、核心约束
├── scripts/                 # 启动入口与运行实现
├── references/              # 双向调用、审查和交接协议
├── assets/                  # 目标工程配置与规则模板
└── agents/openai.yaml       # 可选 Codex 展示元数据
```

发布规则：

- 使用文件白名单，排除开发仓库 `.git/`、`.codex/`、`.agents/sessions/` 和运行日志。
- 每个发布包记录版本和内容摘要，三个安装位置保持一致。
- 正常使用安装发布快照；开发调试可选择链接源码。
- 全局升级后，目标工程规则保持原样；规则迁移单独提供预览。
- V1 优先使用本地 Skill 包。需要对外分发或附带 MCP 时，再增加插件包装。

### 3.2 目标工程布局

以下为协作文件的默认位置，均允许配置：

```text
Target Project/
├── 原有业务代码与测试目录       # 保持项目现有结构
├── AGENTS.md                   # 共享项目规则
├── .codex-loop.toml            # 协作配置
├── docs/codex-loop/tasks/
│   └── <task-id>.md            # 目标、范围、步骤、验收要求
├── .agents/
│   ├── rules/                 # Antigravity 专用规则
│   ├── skills/                # 可供两端发现的项目 Skill
│   └── sessions/              # 双方可读的决策与交接记录
└── .codex/
    ├── config.toml            # Codex 项目配置
    └── reviews/
        └── <task-id>.md        # 审查记录
```

目录区分表达的是**职责归属，不是访问隔离**。实际访问范围由宿主权限和沙箱控制。

`.codex-loop.toml` 仅保存协作设置：

- 配置格式版本与所需 Skill 版本；
- 业务代码、测试及允许修改的路径；
- 验收命令及其工作目录；
- 任务、证据和归档位置；
- 超时与最大修复轮数；
- 可选模型覆盖。

凭据保留在各宿主自己的账户配置中。

### 3.3 目标绑定与路径规则

启动器必须分别解析：

| 路径 | 解析依据 |
|---|---|
| Skill 脚本、模板和参考文件 | 已加载 Skill 的安装位置 |
| 业务工程与子进程工作目录 | `--project` 指定的目标 |
| 任务、审查、测试和归档输出 | 目标工程根目录 |

执行约束：

1. 修改类命令必须明确绑定目标工程；可由宿主提供当前工作区路径。
2. 启动前校验规范化绝对路径、Git 根目录和配置位置。
3. 启动 Codex、`agy` 时，均显式设置 `cwd=target_root`。
4. 相对输出路径以目标工程为基准；解析后校验是否越界。
5. 运行日志记录 Skill 版本、目标目录、任务 ID 和 CLI 版本。
6. 目标工程缺失或绑定不明确时，停止该次执行，不能回退到 Skill 仓库。

### 3.4 项目规则与配置的关系

`AGENTS.md` 保存共享开发规则；宿主专用规则只补充自身行为。

- 初始化时保留目标工程现有规则，只增补可识别的 codex-loop 管理区块。
- 同时尊重适用的目录级规则；发现冲突时报告具体条目。
- Skill 开发仓库的规则仅适用于开发仓库，不直接复制到业务工程。
- Codex 默认继承目标工程及用户配置；未指定模型或推理强度时，不传覆盖参数。
- Antigravity IDE 和 CLI 分别保留自己的配置与登录状态。

Codex 官方支持用户配置及受信任项目的 `.codex/config.toml`；命令行覆盖参数优先于这些默认配置。[Codex 配置文档](https://learn.chatgpt.com/docs/config-file/config-basic)

## 4. 双向互调流程

### 4.1 Antigravity 发起

**用户需求 → Codex 规划 → Antigravity 实施与测试 → Codex 审查 → 修复或交付。**

1. Antigravity 确认目标工程、读取规则，创建任务文件。
2. 全局启动器在目标工程中运行 `codex exec`，规划阶段使用只读权限。
3. Antigravity 按计划实施并执行验收命令。
4. 冻结业务代码修改，运行 `codex review`。
5. 有问题则修复、重新测试、重新审查。
6. 保存审查结果、测试证据与简短交接记录。

### 4.2 Codex 发起

**Codex 规划 → Antigravity CLI 实施与测试 → Codex 审查 → 修复或交付。**

1. Codex 将目标、范围和验收要求写入目标工程任务文件。
2. 启动器在同一目标目录运行 `agy -p`。
3. Antigravity CLI 读取规则与任务，实施后返回结果和测试证据。
4. Codex 检查真实差异，执行审查。
5. 按同样的修复与复审规则完成任务。

`agy -p` 支持无头执行和 JSON 输出。它启动的是 CLI 会话，不能假设它继承当前 IDE 聊天；应通过任务文件和明确的会话 ID 交接。[Antigravity 无头模式文档](https://www.antigravity.google/docs/cli/headless/)

### 4.3 调度约束

- 每项任务只有一个发起方负责推进阶段。
- 被调用方完成当前阶段后返回，不再次启动协作闭环。
- 同一工作目录一次只允许一个实现阶段；审查期间冻结业务修改。
- 分支切换、提交和回退串行执行。
- 不同目标工程可独立运行，分别使用各自的任务和记录。
- 超时或达到修复轮数上限后，保留现场并报告阻断原因。

V1 使用 CLI、文件和阶段交接即可；消息队列与常驻调度服务不进入首期范围。

### 4.4 建议的命令接口

以下是**待实现接口**，现有脚本尚未支持全部参数：

```powershell
# $LoopLauncher 指向全局安装包中的脚本
$TargetRoot = "D:\projects\web-app"

python "$LoopLauncher" info --project "$TargetRoot"
python "$LoopLauncher" init --project "$TargetRoot" --dry-run

  --out "docs/codex-loop/tasks/task-001.md"

  --task "docs/codex-loop/tasks/task-001.md"

```

审查目标 `--uncommitted`、`--base`、`--commit` 必须互斥，自定义审查提示按当前 CLI 支持的方式传入。[Codex 命令参考](https://learn.chatgpt.com/docs/developer-commands?surface=cli)

## 5. 验收与开发规则

### 5.1 区分三种结果

| 结果 | 判定依据 |
|---|---|
| **Agent 调用成功** | 子进程完成并返回有效输出 |
| **验证通过** | 规定检查实际执行，结果符合验收要求 |
| **任务完成** | 验证通过、必要审查通过、修改范围符合计划 |

尤其需要防止：`agy` 无头模式中，需审批的命令可能被跳过，进程仍返回 `0`。因此 `accept-edits` 或进程成功都不能证明测试执行过。[Antigravity 权限说明](https://www.antigravity.google/docs/cli/headless/)

启动器应记录实际测试命令、工作目录、退出码和日志；涉及关键变更时，在最终验收阶段重新运行必要检查。

### 5.2 审查协议

`APPROVED` 是项目约定，不能假设原生 CLI 自动提供固定批准格式。

- 保留原始审查输出。
- 通过规则或受支持的提示方式要求明确结论。
- 仅接受约定结论位置的有效结果；否定、引用和正文关键词不构成批准。
- 输出为空、不完整、结论矛盾或无法解析时，保持“待审查”。
- 审查绑定具体提交及文件内容摘要，包含相关未跟踪文件。
- 审查后代码发生变化，原批准失效。

建议包装层退出码：

| 退出码 | 含义 |
|---|---|
| `0` | 当前操作完成并满足自身要求 |
| `1` | 执行、权限、超时、文件或协议错误 |
| `2` | 审查明确要求修改 |

参数错误仍可沿用 `argparse` 的行为，但日志必须明确标识错误类型。

### 5.3 质量约束

| 约束 | 验收要求 |
|---|---|
| 目标正确 | 从任意启动目录执行，业务读写与输出均归属指定目标 |
| 最小修改 | 实际差异符合任务允许范围；扩大范围需更新计划 |
| 测试证据 | 必要检查真实执行且退出码为 0；不能以零测试或跳过测试放行 |
| 关键审查 | 核心算法、架构、鉴权和跨模块变更取得有效 Codex 审查结论 |
| Git 防灾 | 复杂修改前保存已有工作；新分支本身不能保护未提交改动 |
| 回退范围 | 只撤销本任务变更；全量回退不得覆盖用户已有工作 |
| 配置隔离 | 不复制 Skill 开发配置，不隐式更改全局账户或模型 |
| 权限边界 | 子进程不能绕过父进程权限；无头命令权限不足必须报告 |
| 会话保真 | 归档绑定明确项目与会话，默认保存决策摘要 |
| 发布可追溯 | 发布包、安装版本、运行记录可对应到源码版本 |

## 7. 需要向用户澄清的设计选项

以下问题用于确定实施范围；表中建议值构成本方案的默认假设。

| 优先级 | 需要澄清的问题 | 建议默认值 |
|---|---|---|
| P0 | 首期覆盖 Windows，还是同时支持 Linux、WSL？ | Windows 优先，保留跨平台实现 |
| P0 | 使用 Antigravity IDE、CLI，还是两者都需要？ | 两者都支持，分别安装与验证 |
| P0 | “双向互调”是否允许 Codex 启动独立 CLI 会话？ | 允许，以文件交接；不依赖 IDE 当前聊天 |
| P0 | 目标工程是否全部使用 Git？ | V1 完整闭环要求 Git，非 Git 先提供规划 |
| P0 | 如何获得各工程的验收命令？ | 初始化探测后记录，可按任务补充 |
| P0 | 默认继承模型配置，还是统一固定模型？ | 继承目标工程与宿主配置，支持显式覆盖 |
| P1 | 接入工程时自动修改规则，还是先生成差异？ | 已授权接入时幂等增补；冲突先提供差异 |
| P1 | 所有变更都必须双 Agent 审查，还是仅关键变更？ | 关键变更强制，其余按工程规则 |
| P1 | 全局安装使用发布副本还是源码链接？ | 发布副本；链接作为开发模式 |
| P1 | 保存完整对话，还是只保存决策摘要？ | 摘要默认，完整导出按明确会话选择 |
| P1 | 自动修复最多运行几轮？ | 3 轮，达到上限保留现场并报告 |
| P2 | 是否需要双 Agent 同时写同一个工程？ | 首期串行；并行任务另用工作树 |
| P2 | 仅个人复用，还是需要公开分发？ | 先完成本地全局 Skill，再增加插件包装 |

实施前应优先确定 P0 选项，并选定一个真实外部工程作为首个验收对象。
