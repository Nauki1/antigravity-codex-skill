# 审查与收工规则

当前实战升级采用 v4、明确的四级严重度和连续审查熔断。下文第1至5版保留演进记录；最新行为见文末“实战升级”。

## 第1版：固定验收标准

开工前明确目标、可验证的验收标准、支持范围、不做事项和验收命令。未确认的假设不作为强制验收要求。

规划入口要求输出这些项目。审查入口默认读取目标工程的 `docs/task.md`，也接受显式 `--task`。显式文件缺失、为空或编码错误时停止；未提供文档时遵循用户明确指令与既有功能保证。

任务内容按 SHA-256 快照传入审查。审查期间任务文档变化，本次批准失效。审查不能自行扩大范围；可选命名调整、重构和未来功能不变成强制任务。相关安全、数据完整性和已有功能回归仍属审查范围。

快照通过 CLI 支持的 stdin 提示词传递，避免长文档超过 Windows 命令行长度限制。默认文档从缺失变为出现也会使本次批准失效；带 UTF-8 BOM 的空文档按空文件处理。

## 第2版：问题必须有证据

每个必须修复的发现记录唯一稳定 ID、位置、支持范围内的具体触发条件、预期行为、实际行为、影响和证据。证据可为实际复现，或确定、可达的代码路径；偏好和未来假设不构成已核验缺陷。

结果协议升级为 `codex-loop-review-v2`，包含与原生发现一一对应的证据记录。缺少字段、未经核验、ID 重复或数量不一致时，保持待审查，不能直接派发修改。只说整体错误却没有具体缺陷证据，也不产生返工指令。包装器验证证据契约，实际证据的真实性仍由审查器核对代码和测试。

证据记录复制原生标题及绝对路径、行号范围。包装器核对 CLI 0.159.2 附加的问题列表；多出、缺失或替换条目均不产生修复判定。未知渲染格式保持待审查，不猜测其含义。

## 第3版：允许举证回应

首次审查用 `--out reviews/first.txt` 保存原始报告。实施方可提交 JSON 回应，每条包含 `finding_id`、`position`（`fixed` 或 `disputed`）、`reason` 和 `evidence`。回应必须引用上轮报告中的 ID，并提供修复或反驳证据，不能只说“已经满足”。

```json
{"responses": [{"finding_id": "F1", "position": "disputed", "reason": "该输入不在约定支持范围内", "evidence": "任务文档的支持范围及入口校验路径"}]}
```

```bash
python scripts/codex_loop.py review --previous-review reviews/first.txt --response reviews/response.json --out reviews/second.txt
```

审查方独立核对代码和测试，逐项给出有理由、有证据的裁定：`closed`（修复完成或原指控不成立）、`confirmed`（问题仍成立）、`needs_human`（证据无法解决分歧）。缺失、重复、未知或自相矛盾的裁定不放行；未解决争议返回 `1`，不批准，也不自动要求继续返工。结构有效的待裁定报告仍可保存供下一次讨论使用。

上轮报告与回应按内容快照传入，审查中变化会使结论失效。输出不能覆盖任务文档或讨论输入。包装器保证裁定契约完整；裁定的事实依据仍由独立审查器核验。

## 第4版：聚焦复审并保留关闭记录

提供 `--previous-review` 就进入聚焦复审：逐项核验上轮问题、修复及相关回归。全部旧 ID（包括已关闭和待用户决定的问题）都要延续裁定，不能通过省略或给同一问题换 ID 来结束争议。新的、范围内的实质缺陷仍可凭证据提出。

已关闭的问题通常继续记录 `closed`。只有核验到新事实时才能用 `reopened` 重开，保留原 ID、列入当前发现，并提供额外 `new_evidence` 字段。重复关闭时的证据、没有关闭历史或直接改为 `confirmed` 都不放行。包装器检查结构、ID、直接重复及与上轮相同标题/位置/触发条件的问题换 ID；新证据是否真正构成新事实、语义相同的换名指控仍由审查器核验。

连续复审使用最近一次保存的报告，不跳回早期报告。首次审查仍检查完整的目标差异；复审不能借机追加命名偏好或无关重构。

报告的 `history` 延续原问题的 ID、标题、位置和触发条件，即使问题已关闭也不删除。遗漏或改写历史使本轮结论失效。旧格式报告若只有关闭裁定、没有原问题身份，则须从保留原问题的报告重新复审，不能凭空恢复历史。

修复可能移动行号或更新描述，因此同一 ID 可以追加多个已核验的身份版本，关闭时一并保留。位置比较统一处理路径分隔符和等价单行范围，避免纯格式变化绕过身份检查。

## 第5版：带建议收工与有限修复

当前审查协议为 `codex-loop-review-v3`。`findings` 只收录已核验、确需修复的实质缺陷；可选建议放入 `advisories`，未确定的实质疑点放入 `uncertainties`。审查完成、`acceptance_met=true`、无实质缺陷、疑点或未解决争议时，允许带建议项批准。验收未达标或证据不足不靠删除问题、达到轮次上限来批准。

v2 报告仍可作为历史输入读取，但不能作为当前审查的批准输出。当前 `review --out` 同时保存原报告和 `.context.json`，记录本次审查 ID、工程、任务路径与内容哈希，以及报告哈希。结构有效的待决报告可保存；输出及上下文不能覆盖审查输入。

自动返工使用专门入口：

```bash
python scripts/codex_loop.py fix --review reviews/first.txt --task docs/task.md
```

该入口要求保存的当前协议报告及上下文一致，按同一任务路径在目标工程的 `.codex/codex-loop/` 保存计数。无配置时默认最多 **2轮**；`.codex-loop.toml` 的 `[collaboration].max_fix_rounds` 可在新周期开始前设置正整数（配置读取需 Python 3.11+）。已有周期的上限不能通过调高配置扩大；任务内容改变也不能自动重置。

每轮启动前原子保存计数，失败或中断仍计入。相同审查 ID 不重复派发；即使新审查文字相同，新生成的审查 ID 也可用于下一轮。达到上限、验收变化或存在待决争议时停止，交由用户决定。无已核验缺陷时不启动实施；建议项不消耗修复轮次。按项目单写入约定使用，不提供并发实施调度。

`fix` 返回 `0` 仅表示无需修复或实施入口执行成功，后者仍须核验产物、运行验收命令并独立复审；`1` 表示输入、状态或实施失败；`3` 表示停止自动返工并等待用户决定。禁止用 `exec-agy`、换任务路径、删除计数、手改上下文或调高参数绕过上限。继续新周期须用户明确授权并留下记录，再由用户或按该授权处理旧状态；工具不自动清空。计数损坏时停止，不从零开始。可将 `.codex/codex-loop/` 加入目标工程的 Git 忽略规则。

`exec-agy` 用于初次实施；修复后运行验收命令，再用最近报告聚焦复审并保存新报告。该工具约束通过入口派发的自动返工，不代替人工对事实证据的判断，也不能阻止用户在编辑器中直接修改文件。上下文绑定验收标准和报告；实施方仍须核对报告与当前代码，过期问题用证据回应。

## 实战升级：临时资产、严重度与审查熔断

审查调用和比对临时资产由系统 `tempfile.TemporaryDirectory` 管理，明确在 `finally` 中清理。系统临时目录若被 TMP/TEMP 指向目标工程内，停止调用并报错。禁止代理手工在业务根目录创建 `.review*` 或时间戳临时快照。显式 `--out` 的交付证据与 `.codex/codex-loop/` 的计数/争议报告是持久记录，供后续复审和用户裁决；状态不能被 `--out` 覆盖。

`init` 幂等创建或增补 Git 忽略规则：`.review*`、`.agents/sessions/*.tmp`、`.codex/codex-loop/`，保留既有内容。忽略规则是兜底，不替代临时目录清理，也不删除已经存在的用户资产。

当前输出协议 `codex-loop-review-v4` 的发现增加 `severity`。`advisories` 每条为 `{ "severity": "SUGGESTION" 或 "MINOR", "message": "建议内容" }`。历史 v2/v3 可读，但不能作为当前审查或自动修复输出。

| 级别 | 适用情况 | 判定与退出码 |
|---|---|---|
| BLOCKER / CRITICAL | 数学逻辑错误、数据被篡改/损坏、规定测试非0、违反适用 AGENTS.md 铁律及实质回归 | NEEDS_FIX，2 |
| SUGGESTION / MINOR | 文风、额外理论推导、非核心命名等可选改善 | APPROVED_WITH_NOTES，0，并打印建议清单 |
| 无问题 | 验收达标且无待决事项 | APPROVED，0 |
| 未核验、未完成或结构无效 | 尚无可靠结论 | 待审查，1，不产生盲目返工 |
| 熔断 | 同一任务连续未获批已到上限 | 待用户裁决，3，停止自动执行 |

有建议仍须满足原验收标准，没有实质疑点或未解决争议。原生 CLI 的标题和发现数量继续逐项对应；可选项即使在原生 findings 中出现，也按明确严重度处理。分级真实性由审查器核对证据和代码，不能用小写、未知或缺失级别默认放行；核心缺陷不得为了通过而降为建议。数学、数据、测试和规则违规的分类在提示词中明确约束。

```bash
python scripts/codex_loop.py review --task docs/task.md --max-iterations 3 --out reviews/latest.txt
```

默认同一任务路径最多连续3次未获批审查，跨命令启动持久计数；调用失败、无效报告及中断也消耗一次，防止重复失败不断调用模型。第3次仍未获批就写出《待裁决争议报告》（含各轮最终输出、理由与最近有效证据摘要），返回3；后来再调用 `review` 或 `fix` 不会继续启动模型/实施。到上限的修复结论仍为 NEEDS_FIX，但熔断返回码3优先，调用方必须先看退出码。

当前未获批序列的上限只可降低，不可通过提高参数扩大；验收改变不会重置计数，转为用户裁决。有效批准（含建议批准）结束连续失败序列；后续明确任务的审查开始新的序列。已经熔断的序列不自动清空，需用户明确裁决/授权并记录新周期。原有 `fix` 默认两轮实施预算继续独立生效；通常是初次审查加两次修复复审，共三次审查。建议项不进入修复任务。

同一任务的审查和修复用本地 OS 执行锁互斥；重叠命令快速返回1，不启动第二个模型或实施进程，也不额外消耗轮次。锁所有权在进程结束时由 OS 释放，锁文件属于内部持久记录。可捕获中断也会记录结果并在上限时落盘熔断；若进程被强制终止，后续修复仍检查已消耗计数，不能利用未完成的状态收尾继续执行。

四阶段与卡片规则见 [阶段协议](phase-checkpoints.md)。Phase 3 未通过或熔断时停留在该阶段，不能声称 Phase 4 已完成或提交交付。
